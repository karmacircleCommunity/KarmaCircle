# Layout & Navigation

Chrome shared across pages: navbar, footer, header banner, modal shell, loading spinner, scroll-progress bar, back-to-top button, and the per-page `<Helmet>`/SEO pattern.
None of these are rendered by a shared layout route — every page imports `<Navbar />` and (usually) `<Footer />` individually at the top of its own JSX, since routing has no nested/layout routes (see [architecture.md](./architecture.md)).

## `Navbar`

[apps/web/src/components/Navbar.tsx](../../apps/web/src/components/Navbar.tsx).
Nav links are a local hardcoded array: Organizations `/organizations`, Events `/events`. No "Home" entry (removed August 2026 — see below); the `/` route itself is unaffected, this only changed what the nav renders. Trending and Shops were also dropped from the array in August 2026, when both of those pages were deleted outright - see [donate-shop-trending.md](./donate-shop-trending.md).
Responsive behavior is pure CSS (`min-[900px]:flex` on the link row, `max-[900px]:block` on the hamburger/avatar trigger — not a `window.resize` listener/`windowWidth` state, despite an earlier version of this file claiming otherwise): above 900px shows the horizontal link row plus either a "Sign Up" CTA or (if Redux's `isLoggedIn` is true) a "Profile ▾" dropdown trigger; below 900px shows a hamburger icon (or the user's avatar image if logged in) that opens a full mobile link panel.

**The two breakpoints didn't actually match, for a real width range (September 2026, caught during a mobile QA pass, unrelated to the sticky/glass work above).** The hamburger/avatar trigger's own `max-*` cutoff was `430px`, not `899px` — so between 431px and 899px (portrait tablets, several phones in landscape) neither element rendered: no link row, no hamburger, no way to reach `/organizations`, `/events`, sign up, or the account menu at all. This file's own line above already described the intended 900px cutoff correctly; the code just didn't match its own documentation. Fixed by moving the trigger to the same `max-[899px]` line the row above uses.

**Off-by-one at exactly 899px (October 2026) — supersedes the `max-[899px]` fix above.** Tailwind v4 compiles an arbitrary `max-[Npx]` variant to the *exclusive* `(width < Npx)`, not the inclusive `(max-width: Npx)` CSS's own `max-width` property implies, so `max-[899px]:block` only fired below 899px, not at it — a real 1px gap against `min-[900px]:flex` (`width >= 900px`) where, once again, neither element rendered. Confirmed live at a 899px viewport. Fixed by matching the number in both variants (`max-[900px]`, `width < 900px`), which pairs with `min-[900px]` with zero gap and zero overlap — that is the correct pairing in v4's range syntax, not an off-by-one itself.
The account dropdown (`.nav_dropdown`) is toggled by directly mutating the DOM (`document.querySelector(".nav_dropdown").classList.toggle(...)`) rather than React state — this only exists once per page since `Navbar` itself is rendered once, so it's safe today but is worth noting if `Navbar` is ever rendered more than once on a page.
The dropdown links to `/user/setup` (Edit profile) or `/dashboard` depending on `user?.userType`, and (for organization users only) `/organization/events` — the organization's own events page, behind the setup gate. That entry used to point at `/event/create`, a path no route has ever matched, so it was a 404 for every organization that clicked it.

**Mobile avatar trigger accessibility (September 2026):** the `<img>` that opens the mobile link panel when logged in used to be a bare, non-interactive image (`alt=""`, no role, not in the tab order) — a keyboard or screen-reader user had no way to reach the mobile account menu at all. It now carries `role="button"`, `tabIndex={0}`, `aria-label="Open account menu"`, `aria-haspopup="true"`, `aria-expanded`, a `focus-visible` ring (the same `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-brand` treatment used elsewhere — see [ui-kit.md](./ui-kit.md)), and an Enter/Space `onKeyDown` handler alongside its existing `onClick`.

**Individual profile navigation (October 2026):** desktop and mobile both show Edit profile, opening `/user/setup` directly.
Organization accounts retain Dashboard.
The sparse `/user/:userName` screen was deleted.

**Settings/Support entries removed (September 2026):** the dropdown's "Settings" and "Support" `<Link>`s never had a `to` prop — dead entries that went nowhere and gave no feedback on click (previously tracked in [known-issues.md](./known-issues.md)). Dropped rather than built out, per that entry's own guidance ("a menu item that silently does nothing is worse than an absent one"); build real Settings/Support pages and re-add the links if/when those exist.
An organization whose profile is still a draft also gets a **"Finish setting up"** entry at the top of the dropdown (and of the mobile sheet), linking to the step where its first missing field lives — that is the always-visible way back into a flow the account is free to skip. See [organizations.md](./organizations.md#the-setup-flow--organizationsetup).
Logout: calls `Logout()`, then `resetUserData()` + `localStorage.clear()` (see [state-management.md](./state-management.md) for how this compares to the other two logout call sites).

**Brand mark (August 2026):** the old `MilanNavBrand.svg` image (a colored wordmark that clashed with the site's rebranded muted-clay palette — see [ui-kit.md](./ui-kit.md)) is gone from this file, replaced by a plain text mark (`--color-brand` dot + brand name) built from the same tokens as everywhere else. `Footer.tsx` now builds the identical mark (white text instead of `text-brand-secondary`, for its dark background) instead of importing the old SVG — see below, the two are consistent again as of the same redesign that rebuilt the footer. The text itself reads "KarmaCircle" as of the site-wide NgoWorld → KarmaCircle rebrand (also August 2026); the wordmark image would need to be redone from scratch since the old SVG is gone.

**Lighter nav treatment (August 2026, same pass):** on direct feedback that the nav read as too bold/prominent for a marketing landing page, three things changed together: (1) the "Home" link was dropped from `Links` — the logo already links there, and a persistent nav item for "the page the logo points to" is redundant; (2) the per-link active-route underline (a `border-b-2` div shown under whichever link matched `location.pathname`) was removed entirely, in both the desktop row and the mobile drawer — reasoned as an app-internal-tab pattern (highlighting "which page am I on") that doesn't fit a marketing site, where hover feedback alone is enough; removing it also meant `useLocation()` is no longer used anywhere in this file (deleted along with it — don't reintroduce a `location.pathname` check without first checking whether the underline it was for should really come back too); (3) both the logo and the nav links themselves dropped a weight/size step (logo: `text-2xl font-semibold` → `text-xl font-medium`; links: `font-medium text-brand-secondary` → `font-normal text-ink/65`, gaining a `hover:text-brand-secondary` color transition in place of the old permanent active-state color). The two hardcoded `text-[#8c321b]` link colors that predated this pass were also replaced (first with `text-brand-secondary`, then folded into the `text-ink/65` change above) — same "off-theme raw hex" reason as the brand-mark change.

**Hover micro-interactions (August 2026):** added in the site-wide motion pass ([ui-kit.md](./ui-kit.md#motion)) and deliberately *not* a reinstatement of the active-route underline removed above — none of them indicate state, they only acknowledge the pointer. Desktop links get a 1px brand rule that wipes in from the left on hover and, on leaving, continues out to the right (`after:origin-right` at rest, `hover:after:origin-left`), which reads as a swipe rather than a rubber band. The logo is a `group`: hovering anywhere on it scales the brand dot and shifts the wordmark to `text-brand` (the dot is 8px — its own hover area isn't an affordance, the wordmark beside it is). The "Profile ▾" caret nudges down toward the panel it opens. The "Sign Up" CTA lifts on hover alongside the glow it already had. The mobile sheet arrives with `motion-safe:animate-pop-in`. Everything transform-based is `motion-safe:`-prefixed.

**Desktop "Sign Up" CTA visibility:** `Navbar` takes an optional `hideSignUpForHeroCta` boolean prop (default `false`) and hides its own "Sign Up" when it's `true`. Only `Landing.tsx` passes it — its own, much bigger hero CTA makes the navbar's identical button redundant while both are on screen. `Navbar.tsx` itself has no scroll/visibility logic of its own for this: the boolean is fully computed by `Landing.tsx`'s own `ScrollTrigger` (`onToggle`, on the hero CTA row's own ref — see [landing-home.md](./landing-home.md)) and handed down as a prop, not derived from a `document.querySelector`/`IntersectionObserver` inside this file. An earlier version of this feature did use a raw `IntersectionObserver` watching a `data-hero-cta` DOM marker from inside `Navbar.tsx`; it was replaced after a real bug surfaced in testing — see "Known issues" below — in favor of reusing the same GSAP `ScrollTrigger` pipeline `Landing.tsx` already had proven working for its scroll-parallax. No dependency was added for this (no `react-scroll-observer` or similar) either way. Every route other than `/` renders `<Navbar />` with no props, so the CTA there just always shows, same as before this feature existed.

*Collapses out of layout, not just opacity (October 2026).* The button originally only faded (`opacity`, kept in layout via `pointer-events-none` so nothing shifted) — direct feedback was that the dead space it left behind, the width of a button, every time it was hidden, read as a layout bug rather than something deliberate. `Navbar` now also animates `max-width`/`margin-left`/`padding` shut (`transition-all duration-300`, alongside the existing `opacity`), so the button takes zero space once hidden rather than just being invisible in place. Its sibling link row (`Organizations`/`Events`) has no `gap` reserving space for it either way now — the row and button sit in a plain `justify-between` flex against the logo, so when the button's own width animates back in on scroll, the row visibly slides left to make room for it, rather than the button just popping into a pre-reserved gap. This is the same mechanism as the original "kept in layout" choice, inverted: that one optimized for nothing ever shifting, this one treats the shift itself as the desired reveal.

**Known issues:** the `IntersectionObserver`-based version of the CTA-visibility feature above had a real bug, found via direct DOM/CSS-transition inspection in a live browser rather than by reading the code: the observer's callback would occasionally fire in a rapid loop, perpetually restarting the button's `opacity` CSS transition so it got visually stuck a fraction of a percent into the animation (computed `opacity` pinned around `0.99`, never reaching `0` or `1`). Root cause not fully isolated before the whole approach was replaced with the `ScrollTrigger`-based one above, which does not reproduce it — if a similar "stuck mid-transition" symptom shows up elsewhere, `element.getAnimations()` (Web Animations API) is what surfaced this one; a stuck `CSSTransition` with a `currentTime` that never grows past a few ms across repeated checks is the signature.

**Made actually sticky, given a liquid-glass material, and made conditional on route/auth (September 2026, three passes).**

*Pass one — the bar was never truly sticky, anywhere.* The `sticky` Tailwind utility only sets `position: sticky` — CSS also requires an inset (`top`/`bottom`/`left`/`right`) before an element can stick, and this file had `sticky` with no `top-*` on it, the one `sticky` row in the app that didn't pair the two. It rendered as `position: static` for as long as the class existed. Fixed by moving `sticky top-0` onto the `<nav>` element itself (previously only on the `max-w-6xl` div inside it — see the "full-width vs. centered" note below for why that also moved). Reported alongside it: `Organizations.tsx` and `Events.tsx` (the only two pages that deviate — see [organizations.md](./organizations.md) and [events.md](./events.md)) wrapped their content in `max-w-7xl`, wider than `Navbar`'s own `max-w-6xl` and every other page's container; fixed by bringing both down to `max-w-6xl`.

*Pass two — `/` still didn't stick, after pass one shipped.* `top-0` alone wasn't sufficient there because `Landing.tsx` wrapped `<Navbar />` and the hero in one shared `flex min-h-dvh flex-col` box (the trick that let the hero fill exactly "the viewport minus the navbar" with no hardcoded guess — see [landing-home.md](./landing-home.md)). `min-h-dvh` caps that box at exactly one viewport tall, and `position: sticky` can never stick past the edge of its own containing block — so the moment the page scrolled past the first screen, Navbar's containing block had already scrolled fully out of view, and the "stuck" nav went with it. Confirmed live (`nav.getBoundingClientRect().top` going negative past exactly one `dvh` of scroll). The obvious-looking fix — wrap `<Navbar />` in its own plain `<div>` instead, just for a measurement ref — reintroduced the *identical* bug one level down: a sticky element's containing block is its immediate parent, and a wrapper that auto-sizes to exactly `<nav>`'s own height gives it zero room to move within, which is just as fatal as a viewport-tall one. Proven live with a throwaway sticky probe `<div>`: identical markup stuck correctly as a bare child of `.app` (thousands of px tall) and failed the same way the moment it was wrapped in a tightly auto-sized div. The actual fix has no wrapper at all — `Navbar` now takes `ref` via `forwardRef` (attached to `<nav>` itself) purely so `Landing.tsx` can measure its real height for the hero's `min-height: calc(100dvh - navHeight)`, while `<Navbar />` stays a bare top-level element, exactly how `/organizations` and `/events` already render it.

*Pass three — conditional stickiness, a route/auth rule, not a per-page prop.* Direct feedback: sticky reads as right on `/` (the hero's "Sign Up" needs to stay reachable the whole scroll) and on `/organizations`/`/events` too, but only for a visitor who hasn't signed up — once logged in there's no "Sign Up" left for a sticky nav to keep surfacing, so it just eats scroll real estate for the rest of that page. `Navbar.tsx` now computes `isSticky = isHome || !isLoggedIn` internally (`useLocation().pathname === "/"` plus the existing `isLoggedIn` selector) and applies `sticky top-0` only when true; every page still renders bare `<Navbar />` with no new prop, since this is meant to be one consistent rule, not something each page opts into. Re-adding `useLocation()` here is unrelated to the per-link active-route underline the August 2026 "lighter nav treatment" pass removed (see above) — that pattern is not back, this is a route check for positioning, not for rendering a different link state.

**Material — real refraction, not flat glassmorphism (September 2026, also revised once).** The first pass reused `EventMobileActionBar`'s recipe verbatim — `backdrop-blur-2xl backdrop-saturate-150` over `bg-white/55`, nothing else — and on review read as a flat frosted, tinted pane with no actual bend to it, not "Liquid Glass." Real Apple-style Liquid Glass comes from displacing the pixels behind the material, not just blurring them: `<nav>` (still full-width, not the `max-w-6xl` div inside it, so the effect spans edge to edge while the link row lines up with every other page's content) now sits over a hidden inline SVG `feDisplacementMap` filter (`#nav-glass-refraction`, defined in `Navbar.tsx` right above the `<nav>` it serves), fed by a `feTurbulence` noise field that's Gaussian-blurred *before* it drives the displacement — unblurred turbulence reads as static/water; blurring it first is what turns it into the smooth, large-scale bend real glass has. Applied via `style={{ backdropFilter: "url(#nav-glass-refraction) blur(16px) saturate(1.7)" }}` rather than Tailwind's `backdrop-blur-*`/`backdrop-saturate-*` utilities, which compose into one shared property behind the scenes and don't leave a clean way to splice in a `url(#id)` filter reference ahead of them. Verified live against this page's own busiest backdrop (`DrivesRail`'s photo cards): their top edges visibly warp passing under the bar. Border/tint/shadow are unchanged from the first pass — full recipe and the shared vocabulary with `EventMobileActionBar`: [design-system/06-radius-elevation.md](./design-system/06-radius-elevation.md#liquid-glass).

*Degrades safely, not silently broken.* Safari and older Firefox don't resolve an SVG filter referenced from `backdrop-filter` — confirmed as a current, live gap in every OSS "Liquid Glass" implementation checked while researching whether to depend on one instead of building this directly (see below), not something introduced here. Per the CSS Filter Effects spec, an unresolvable filter *function* within a list is dropped, not the whole property, so those browsers still render the `blur`/`saturate` behind it — the first pass's result, not a broken one; only the extra bend is Chromium/Blink-only today.

*Considered and rejected: an npm "Liquid Glass" library.* Researched several (`rdev/liquid-glass-react`, `PallavAg/liquid-glass-web-react`, `glincker/glinui`, among others) before building the filter above by hand. The most credible by adoption, `rdev/liquid-glass-react` (6.2k GitHub stars, MIT), is ~34KB gzipped and last published June 2025 (15+ months stale as of this writing); its entire API (`elasticity`, `mouseContainer`, cursor-follow "wobble") and every example in its own README (buttons, cards) target small floating widgets, not a static full-width bar. This app already removed a 230KB Three.js hero specifically to cut decorative-effect weight (see `Landing.tsx`/`HeroScene.tsx`) — paying a third of that, sitewide, on every route, for a mismatched widget wasn't the right trade for a component this reused. The technique underneath all of them (SVG `feDisplacementMap` over `backdrop-filter`) is plain CSS/SVG; building it directly costs zero added bytes and was verified visually in-browser before shipping rather than taken on faith. Revisit if a future need (e.g. a real interactive lens/magnifier element) matches one of these libraries' actual design center better than this app's own hand-rolled filter does.

*Pass four — tint brought near-zero (October 2026).* Direct feedback: the `bg-white/55` fill (shared with `EventMobileActionBar`, see [design-system/06-radius-elevation.md#liquid-glass](./design-system/06-radius-elevation.md#liquid-glass)) read as a painted-on white bar, not glass, once live — at 55% white the fill dominates over whatever's actually scrolling underneath, especially since much of this app's own content is itself near-white, so there was little visible contrast to show the effect off against in the first place. Before picking a replacement number, checked how two sites known for an always-visible glass/blur header actually do it: Linear's header computes to `background: rgba(0, 0, 0, 0)` — no fill at all — plus `backdrop-filter: blur(20px)` and a `rgba(255, 255, 255, 0.08)` hairline border, relying entirely on the blur/saturate filter (not the fill) to read as glass, which tracks — `backdrop-filter` blurs whatever is behind an element regardless of that element's own opacity. Vercel's header is `bg-transparent` with no blur at rest at all, only gaining a solid background once scrolled (a `data-scrolled` state swap) — a different pattern (transparent-then-solid, not always-glass) and not what this app wants, since `Navbar` needs to stay legible over arbitrary scrolled content the whole time, not just at the top of the page. Landed between the two: `bg-white/10 border border-white/15` (was `bg-white/55 border-white/40`), rim-light eased from `rgba(255,255,255,0.65)` to `rgba(255,255,255,0.4)` to stay proportional to the lighter fill. Not matching Linear's literal zero fill — on this app's often near-white backgrounds, zero fill plus blur stopped reading as "glass" entirely and started reading as "is the bar even there." `backdrop-filter` itself (blur/saturate/refraction, all above) is unchanged; the fill was the only thing that needed to come down. `EventMobileActionBar` is deliberately untouched — it's a small floating capsule, not an edge-to-edge bar sitting over the page's full visual variety, so its original 55% tint still reads fine there; this is a per-surface tint call, not a system-wide one.

## `Footer`

[apps/web/src/components/footer/Footer.tsx](../../apps/web/src/components/footer/Footer.tsx).
Rebuilt August 2026 into a minimal, three-band premium/dark footer (`bg-surface-dark`, see [ui-kit.md](./ui-kit.md) for that token) in place of the previous single-row `bg-[#1b1b1b]` layout: a top newsletter band (heading/subcopy + an email input and "Subscribe" button), a middle band (brand mark + tagline + socials, alongside the three link columns), and a bottom copyright bar (centered text). The link columns are still purely data-driven from [apps/web/src/components/footer/footerLinksConfig.ts](../../apps/web/src/components/footer/footerLinksConfig.ts): `quickStarts`, `resources` (external links open in a new tab if the path starts with `http`), `policies` (`/terms`, `/privacy`, `/cookies` — none of these routes exist in `routesConfig.tsx`), and `social` (LinkedIn/X/GitHub icons, mapped through a local `socialIcons` lookup keyed by the string names `FaLinkedinIn`/`FaXTwitter`/`FaGithub`). To add a footer link, edit `footerLinksConfig.ts` rather than this component. The old mobile-only duplicate render of the policies links (a second copy of the same list, shown only below 500px) is gone — the redesign's `flex-wrap` link-column layout wraps naturally at narrow widths instead, so there's only one copy of that markup now.

**Mobile layout (fixed August 2026):** all three bands share one `px-9 py-10` → `lg:px-12 lg:py-16` padding scale, deliberately tighter on mobile (`py-10`/`py-8` vs. `lg:py-16`/`lg:p-12`) than the original always-`py-16`/`py-12` version, which made the footer disproportionately tall and padding-heavy on small screens. Text stays left-aligned at every breakpoint (`items-start` on the newsletter row, no `text-center` on any heading/paragraph) — confirmed against mobile-footer conventions at large (GitHub, Stripe, Vercel, Airbnb, Apple all left-align footer body content; centering is reserved for short hero copy, not link/newsletter text) rather than switched to centered. Because left-aligned text sits flush against the container edge with no auto-margin illusion of breathing room, the horizontal padding was bumped from the original `px-8` (32px) — briefly all the way to `px-10`/40px, then settled at `px-9`/36px on direct feedback that 40px read as too much (`lg:px-12` unchanged throughout). Below `lg`, the three link columns (which sit side-by-side with the brand block on `lg:flex-row`) get a `border-t border-white/5 pt-8` divider so the stacked mobile layout reads as two distinct groups (brand+social, then links) instead of one long undifferentiated column.

**Mobile type scale (fixed August 2026, same pass):** every text size in the footer that wasn't already the smallest token (`text-caption`, 10px — the uppercase column labels and the copyright line) now steps down one size on mobile and back up at `sm:`, on direct feedback that the desktop sizes read as oversized on a narrow column: the "Stay connected." heading `text-3xl`→`text-2xl sm:text-3xl`, its subcopy and the email input/Subscribe button `text-body-lg`→`text-sm sm:text-body-lg`, the "KarmaCircle" brand mark `text-xl`→`text-lg sm:text-xl`, and the brand tagline plus every link in the three columns `text-body`→`text-xs sm:text-body`. No change to the `sm:`/`lg:` sizes themselves, only what mobile falls back to below them.

**Newsletter form:** local `email` state + a controlled `<input type="email">`; `onSubmit` calls `event.preventDefault()` and, if the field is non-empty, shows a `showSuccessToast` acknowledging interest and clears the field. There is no newsletter endpoint in `KarmaCircleApi.ts` or `apps/api` — nothing is actually sent or stored anywhere. This is a deliberate middle ground between silently doing nothing (like `Profile.tsx`'s non-functional Subscribe button) and claiming a real subscription happened; see [known-issues.md](./known-issues.md).

**Parallax (August 2026, same pass; desktop-only as of the mobile-layout fix above):** a `useGSAP` call, scoped to the `<footer>` itself, ties the newsletter band and the links band to two different `yPercent` scrub tweens (`-16`/`-8`) against one shared-shape `ScrollTrigger` (`start: "top bottom"`, `end: "bottom bottom"`, `scrub: true`) — the speed difference between the two bands is what reads as parallax, not a single block translating as one rigid unit. Each tween gets its own freshly-built `scrollTrigger` vars object (a `makeScrollTrigger()` factory, not one object reused across both `gsap.to()` calls) — GSAP stamps a back-reference onto whatever vars object it's given when it builds the `ScrollTrigger` instance, so sharing one object between two tweens would let the second call's stamp overwrite the first's and orphan that ScrollTrigger. `end: "bottom bottom"`, not Landing.tsx's `"bottom top"`: Footer is always the last element on the page, so the viewport can never scroll far enough for the footer's bottom edge to reach the viewport's *top* (there's nothing below it left to scroll into) — `"bottom bottom"` (the footer's bottom edge reaching the viewport's bottom edge) is the actual maximum reachable scroll position, so that's the range the scrub uses to reach full progress. Skipped under `prefers-reduced-motion`, same convention as `Landing.tsx`/`HeroScene.tsx` — no `gsap.set` needed to restore a resting state here, since (unlike Landing's fade-in) both layers start at their natural rendered position with no initial offset applied. Also skipped below `lg` (`window.matchMedia("(min-width: 1024px)")`): on a short mobile viewport the same `yPercent` translate covers a much bigger share of the (much taller, relative to viewport) footer, and was visibly eating into the padding above "Stay connected." as the page scrolled — see mobile-layout note above.

**Made resize-reactive (fixed August 2026, same pass):** the `lg:` check above was originally read once at mount, same one-time convention as the reduced-motion check — which covers a page that *loads* at a given width, but not one that's *resized* across the 1024px line without a full reload (a dev-tools device-dimension change, or a real browser window resize/tiling). In that case the component never remounts, so the stale mount-time read left the parallax running (or not) at the wrong width — reintroducing the exact "eating the top padding" bug through the resize path instead of the mount path. Fixed the same way `Landing.tsx` already handles its own `windowWidth`-gated branch: a `resize` listener feeds a `windowWidth` state value into `useGSAP`'s `dependencies` array, so the whole effect reverts and re-runs on every resize, not just on mount. That alone wasn't sufficient, though — verified in-browser that `useGSAP`'s automatic revert doesn't reliably clear a scrub tween's *in-flight* inline `transform` (as opposed to one that never started animating), so the `!isDesktop` branch also explicitly runs `gsap.set([newsletterRef.current, linksRef.current], { clearProps: "transform" })` before returning, rather than relying on revert timing to do it.

## `Loading`

[apps/web/src/components/Loading.tsx](../../apps/web/src/components/Loading.tsx).
A spinning-ring loading indicator, styled with Tailwind (`animate-spin` + a transparent-right-border trick to mimic Bootstrap's old spinner look, plus `sr-only` for the "Loading..." text). Bootstrap itself has been fully removed from the app (was previously loaded via a `<link>`/`<script>` CDN pair in `index.html`) — this component no longer depends on it.
Used as the "no data yet" fallback in `Organizations.tsx` and `Events.jsx` (though, per [organizations.md](./organizations.md)/[events.md](./events.md), those arrays are currently always populated with hardcoded data, so the fallback branch is effectively unreachable today), and in `Donate.tsx` (unrouted — see [donate-shop-trending.md](./donate-shop-trending.md)).

## `ScrollProgress`

[apps/web/src/components/ScrollProgress.tsx](../../apps/web/src/components/ScrollProgress.tsx).
A 2px brand-gradient rule pinned across the top of the window that fills as the page scrolls. Mounted once in `App.tsx`, outside `<Routes>`, so it covers every route and isn't re-created on navigation.
Driven by a GSAP `ScrollTrigger` on `document.documentElement` rather than a `window.scrollY` listener: the app's real scroll position is Lenis's eased one (`SmoothScroll.tsx`), and a raw listener would visibly run ahead of the page it describes. `scrub: 0.2` gives it a small trailing ease.
`aria-hidden` and `pointer-events-none` — it's decorative. Under `prefers-reduced-motion` it simply never animates, staying at zero width (invisible), rather than being parked at a static fill describing a scroll position nobody is at.

## `BacktoTop` (built, not mounted)

[apps/web/src/components/buttons/BacktoTop.tsx](../../apps/web/src/components/buttons/BacktoTop.tsx).
No longer rendered by `App.tsx` as of August 2026 (removed on direct feedback that the floating scroll-to-top button didn't fit the site's cleaner, more minimal look) — still exported from `apps/web/src/components/index.ts` and otherwise fully working (shows a scroll-to-top arrow once `document.documentElement.scrollTop` exceeds 250px, debounced 300ms via a small hand-rolled `debounce` helper defined inline in the component), so re-mounting it in `App.tsx` (or anywhere else) is a one-line change if it's ever wanted back.
Still unmounted after the August 2026 motion pass — that pass deliberately left it alone rather than taking "add subtle interactions site-wide" as licence to reintroduce chrome that was removed on direct feedback. `ScrollProgress` (below) covers the "how far through am I?" half of what this button offered, without a floating element.

## `ClickAwayListener`

## `ComponentHelmet` (per-page SEO)

[apps/web/src/components/ComponentHelmet.tsx](../../apps/web/src/components/ComponentHelmet.tsx).
A `type`-keyed `<Helmet>` wrapper supporting `"Organizations"` and `"Events"` (exact string match, case-sensitive); returns `null` for anything else.
Used by `Organizations.tsx` (`type="Organizations"`, correct) and `Events.jsx` (`type="Events"`, correct — fixed August 2026, was previously `type="Organizations"`; see [events.md](./events.md)).
Most other pages (`Home`, `Auth`, `Donate`) instead inline their own `<Helmet>` block directly rather than extending this component — if you add a new page needing SEO tags, either extend `ComponentHelmet` with a new `type` branch (consistent with `Organizations`/`Events`) or follow the inline-`<Helmet>` pattern (consistent with `Home`/`Auth`); both exist today, no single convention has won yet.
